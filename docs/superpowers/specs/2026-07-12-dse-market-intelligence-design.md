# Vectora — DSE Market Intelligence System: Design Specification

**Date:** 2026-07-12
**Status:** Draft for user review
**Constraint that shapes everything:** Total cash cost must be $0. No paid APIs, no paid cloud, no paid data.

---

## 0. Decisions Already Made (user-confirmed)

| Decision | Choice |
|---|---|
| First deliverable | Full design spec (this document); implementation in later sessions |
| Runtime | GitHub Actions free tier (private repo), scheduled workflows |
| Alerts | Email via Gmail SMTP (daily digest + urgent alerts) |
| Reasoning layer | **No LLM in the loop** — pure ML/statistics, lexicon-based text processing, templated explanations |
| Persistent memory | Obsidian vault, machine-generated from structured data, stored in the same git repo |

### Consequences of "No LLM in the loop" (read this first)

The original vision described AI agents that "interpret news" and "write knowledge." Without an LLM:

- **News/sentiment analysis** becomes keyword-lexicon and rule-based classification (event type detection from announcement titles, a small finance sentiment lexicon). It will be cruder but deterministic and free.
- **Explanations** come from SHAP feature attributions rendered through templates, plus retrieval of similar historical episodes. They will be formulaic but honest and reproducible.
- **The Obsidian vault** is generated by code from structured data (Jinja2 templates over the database). It is a knowledge *mirror*, not a knowledge *author*. Human notes live alongside and are never overwritten.
- **"Agents"** become deterministic Python pipeline modules with single responsibilities. Same modularity, no token cost, no non-determinism.

This can be upgraded later (Phase 6 in the roadmap) by plugging Claude Code sessions or a local LLM into the news/memory modules without changing the architecture — the module boundaries are designed for that.

## 1. Scope and Non-Goals

### In scope
- Daily-cycle EOD data collection for all DSE-listed instruments (~650 securities incl. ~360 equities), plus intraday snapshot scans during trading hours for anomaly alerts.
- Multi-horizon **probability forecasts** (P(move ≥ threshold within horizon)) with calibration, not point price predictions.
- Anomaly detection: volume spikes, abnormal volatility, pump-and-dump pattern scores, pre-announcement drift patterns — all from **public data only**.
- Z-category specialist module.
- Market regime classification.
- Event capture: DSE/BSEC announcements, corporate actions, news headlines.
- Risk metrics attached to every signal; explainability for every signal.
- Email alerting with urgency tiers; Obsidian vault as the knowledge base and reading UI.
- Prediction logging, outcome evaluation, calibration tracking, and scheduled retraining (the continuous-learning loop).

### Non-goals (explicit)
- **No order execution.** DSE has no retail trading API; this is an intelligence/decision-support system. All outputs are informational, not financial advice.
- **No use or inference of non-public information.** The system learns *statistical footprints* of publicly observable behavior (e.g., volume/price patterns that historically preceded announcements) — it flags patterns, never alleges wrongdoing about specific parties.
- **No real-time tick/order-book feed.** Not freely available. "Immediate-term" means intraday snapshot polling (every 30–60 min during trading hours) at best.
- **No 24/7 server.** GitHub Actions cron jobs only.
- **No deep-learning-first modeling.** With ~350 usable equities × daily bars, gradient boosting dominates. DL architectures are evaluated in the model-comparison framework but are not the backbone (see §10).
- **No public redistribution of scraped data.** Private repo.

## 2. The DSE Environment: Facts the Design Must Respect

These characteristics are design inputs, each mapped to a design response. (Phase 0 of implementation includes verifying current parameter values — circuit-breaker bands and category rules change by BSEC directive.)

| DSE characteristic | Design response |
|---|---|
| Low liquidity; many stocks trade < ৳1M/day; thin order books | Liquidity filter on all signals; slippage-aware backtests; "liquidity trap" probability output; position-size guidance capped at % of average daily turnover |
| Retail dominance (~80% of turnover), herd behavior, rumor-driven moves | Momentum/reversal features work differently than in developed markets — regime-conditional models; Google Trends and news-intensity features |
| Circuit breakers (price bands ~±10%, tighter for low-priced/Z stocks) and historical floor-price regimes (2020, 2022–24) | Censored-return handling in labels; "limit-locked" state features; floor-price era flagged as a distinct regime and largely excluded from training or given era dummies |
| Categories A/B/N/Z with different rules (Z: weak fundamentals, no/low dividend, historically longer settlement, margin-loan restrictions) | Category is a first-class entity with full migration history; dedicated Z-module (§13) |
| Slow information diffusion; announcements move prices for days | Event-window features (days since/until event); post-event drift models |
| Documented manipulation patterns (BSEC enforcement orders, academic studies on pump-and-dump in DSE) | Pump-and-dump phase classifier trained on historically labeled episodes assembled from public enforcement records + price/volume signatures (§13) |
| Sudden regulatory intervention (trading halts, margin rule changes, floor prices) | Regulatory-event feed; "regulatory interruption" risk flag on signals; kill-switch regime state |
| Sponsor/director holding disclosures are public and price-relevant | Monthly holding scrape; director-buying features |
| Small cross-section (~350 equities) and short reliable history (~2012+) | Cross-sectional (pooled) models rather than per-stock models; heavy regularization; walk-forward validation; skepticism about deep nets |

## 3. System Architecture

### 3.1 Shape: modular monolith, pipeline-orchestrated

One Python package (`vectora/`) composed of single-responsibility modules (the "agents" of the original brief), executed as DAG stages by a thin orchestrator. GitHub Actions workflows invoke the orchestrator with a stage selector. All state lives in the repo: DuckDB database + Parquet files + Obsidian vault (markdown).

Why not a literal multi-agent framework (LangGraph/CrewAI-style)? Those exist to coordinate LLM calls. With no LLM in the loop, they add dependency weight and non-determinism for zero benefit. Module boundaries give the same separation of concerns.

```
┌─────────────────────────── GitHub Actions (cron) ───────────────────────────┐
│                                                                              │
│  eod-pipeline.yml (daily, post-close)      intraday-scan.yml (hourly, mkt hrs)
│  train.yml (weekly)                        evaluate.yml (daily, pre-open)    │
└──────────────────────────────┬───────────────────────────────────────────────┘
                               │  python -m vectora run <stage>
                               ▼
   ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐
   │  collect    │→ │  validate   │→ │  features   │→ │  regime     │
   │ (scrapers)  │  │  + clean    │  │  engine     │  │  detector   │
   └────────────┘   └────────────┘   └────────────┘   └──────┬─────┘
   ┌────────────┐   ┌────────────┐          ┌────────────────▼─────┐
   │  events     │→ │  sentiment/ │───────→ │  predict              │
   │ (announce-  │  │  event      │          │  (model inference,    │
   │  ments,news)│  │  classifier │          │  prob. forecasts)     │
   └────────────┘   └────────────┘          └──────────┬───────────┘
                                   ┌───────────────────▼──┐   ┌──────────────┐
                                   │  risk engine          │→ │  explain      │
                                   └───────────────────┬──┘   │ (SHAP+templ.) │
   ┌────────────┐   ┌────────────┐                     ▼      └──────┬───────┘
   │  evaluate   │← │  outcomes   │              ┌────────────┐      ▼
   │ (calibr.,   │  │  resolver   │              │  alerts     │  ┌──────────┐
   │  retrain    │  └────────────┘              │ (email)     │  │  vault    │
   │  triggers)  │                               └────────────┘  │ (Obsidian)│
   └────────────┘                                                └──────────┘
```

### 3.2 Module (“agent”) responsibilities

| Module | Single responsibility | Key outputs |
|---|---|---|
| `collect` | Fetch raw data from each source; never transforms | Raw Parquet/JSON in `data/raw/`, source metadata |
| `validate` | Schema, range, continuity, cross-source consistency checks | Data-quality scores per source/day; quarantine of bad rows |
| `clean` | Corporate-action adjustment, gap handling, canonical symbols | `prices_adjusted` table |
| `features` | Compute the feature matrix incrementally (only new dates) | `features` Parquet, feature registry with documented reasoning |
| `regime` | Classify market regime (rules + HMM) | `regime` table, regime-change events |
| `events` | Scrape/normalize announcements, news, corporate actions | `events` table with typed events |
| `event_classifier` | Rule/lexicon classification of event type + crude sentiment | Event type, polarity, materiality score |
| `predict` | Load trained models, emit calibrated probabilities | `predictions` table (one row per stock×horizon×threshold) |
| `risk` | Attach risk metrics to every prediction | Risk block per signal |
| `explain` | SHAP attributions + historical-analog retrieval + template render | Explanation text per signal |
| `alerts` | Rank, deduplicate, throttle, send email | Sent-alert log |
| `vault` | Regenerate/append Obsidian notes from DB (never touch human notes) | Markdown files |
| `outcomes` | Resolve matured predictions against realized prices | `outcomes` table |
| `evaluate` | Calibration, hit-rate, drift metrics; retrain trigger | Evaluation reports, `models/registry.json` |
| `train` | Walk-forward training + model comparison + calibration fitting | Versioned model artifacts |

Every module: pure-ish function of (DB state, config) → (DB state, artifacts), idempotent per run-date, unit-testable in isolation.

## 4. Technology Stack (all free/open-source)

| Layer | Choice | Why |
|---|---|---|
| Language | Python 3.12 | Ecosystem; bdshare compatibility |
| Scraping | `requests` + `beautifulsoup4` + `lxml`; `bdshare` as reference/fallback | dsebd.org is server-rendered HTML — no browser automation needed for most pages |
| Dataframes | `polars` (with pandas interop where libs require it) | Speed on Actions runners; lazy scan of Parquet |
| Storage | **DuckDB** + Parquet files, committed to git | Zero-server analytical SQL; single file; git-friendly with periodic compaction; Parquet raw layer keeps DB rebuildable |
| ML | **LightGBM** (primary), scikit-learn (baselines, calibration), `hmmlearn` (regimes), SHAP | Best-in-class for small/medium tabular; fast enough to retrain weekly on free runners |
| Stats | `statsmodels`, `scipy` | Tests, conformal intervals |
| Trends | `pytrends` (Google Trends, unofficial but free) | Search-interest features; treated as best-effort source |
| Templates | Jinja2 | Vault notes, email bodies, explanations |
| Email | Gmail SMTP + app password (stored as GitHub Secret) | Free; 500 recipients/day limit is irrelevant at our volume |
| Scheduling | GitHub Actions cron (UTC; Dhaka = UTC+6, no DST) | Free tier |
| Dashboard (later) | Static HTML report committed to repo / GitHub Pages | No server |
| Tests | pytest + recorded HTML fixtures (`responses`) | Scraper tests without hitting live site |

Rejected: PostgreSQL (needs a server), Airflow/Prefect (overkill for 5 workflows), TimescaleDB, Docker in CI (slower cold start), cloud feature stores.

## 5. Data Sources and Collection Pipeline

### 5.1 Source inventory (all free, all public)

**Tier 1 — core, scraped daily:**

| Source | What | Method | Cadence |
|---|---|---|---|
| dsebd.org day-end archive (`data_archive.php`) | OHLCV, turnover, trades per instrument | HTML scrape (bdshare-style) | Daily post-close |
| dsebd.org latest share price pages | Intraday snapshot: LTP, high, low, volume, value | HTML scrape | Hourly during trading |
| dsebd.org company pages (`displayCompany.php`) | EPS, NAV, dividend history, category, sector, sponsor/director/institute/public holding %, paid-up capital, loan info | HTML scrape | Weekly full sweep + on-event |
| dsebd.org news/announcements (`old_news.php`, company news) | Corporate announcements: dividends, board meetings, earnings, spot news, category changes, trading halts | HTML scrape | Every run |
| dsebd.org indices pages | DSEX, DSES, DS30, sector indices | HTML scrape | Daily |
| dsebd.org block/market data pages | Block transactions | HTML scrape | Daily |

**Tier 2 — periodic/backfill:**

| Source | What | Method | Cadence |
|---|---|---|---|
| Mendeley DSE EOD dataset (2012–2026) | Historical OHLCV backfill | One-time download | Once, Phase 1 |
| AmarStock CSV download | Cross-validation of EOD data; gap fill | CSV download | On demand |
| BSEC website (press releases, enforcement) | Regulatory actions, directives, enforcement orders | HTML scrape of press-release list | Daily |
| Bangladesh Bank statistics | Repo/call rates, inflation, FX (USD/BDT), reserves | HTML/XLS scrape | Weekly |
| DSE monthly review / listed-company financials | Quarterly EPS/NAV/NOCFPS as announced | Announcement parse + company page | On event |

**Tier 3 — alternative, best-effort (graceful degradation if they break):**

| Source | What | Notes |
|---|---|---|
| Google Trends via pytrends | Search interest for tickers/company names/"share bazar" terms | Rate-limited; weekly batch |
| News RSS (The Daily Star business, The Financial Express, TBS, Prothom Alo business) | Headlines mentioning listed companies | Headline-only capture + lexicon tagging; full-article NLP is out of scope without LLM |
| Global/regional context | Yahoo Finance public endpoints for oil, USD index, SENSEX, MSCI FM proxies | Small daily fetch |

Explicitly **excluded**: Facebook groups/YouTube scraping (ToS-violating, brittle, and low signal-to-noise without an LLM), any paid feed, LankaBD level-2 data (account-gated).

### 5.2 Collection rules

- Every scraper writes **raw, untransformed** payloads to `data/raw/<source>/<date>/` before any parsing — reprocessing is always possible.
- Per-source `SourceMeta`: URL, fetch time, HTTP status, row count, checksum. Stored with the data.
- Politeness: sequential requests, 1–2 s delay, identifying User-Agent, retries with backoff, hard timeout. Total daily load on dsebd.org: a few hundred requests — comparable to one human browsing session.
- Every parser is paired with recorded HTML fixtures; a **layout-change canary** (structural hash of key pages) fails loudly in `health.yml` when DSE redesigns a page.
- Trading calendar maintained in `data/reference/holidays.csv` (Bangladesh holidays + special closures); intraday scans skip non-trading days.

### 5.3 Data validation gates (the `validate` module)

1. **Schema**: column presence/types per source.
2. **Range**: prices > 0; |daily move| ≤ circuit band unless flagged; volume ≥ 0.
3. **Continuity**: every active symbol has a row every trading day (or an explicit halt/no-trade marker).
4. **Cross-source**: weekly DSE-vs-AmarStock EOD spot check on a rotating sample; discrepancies quarantined.
5. **Corporate-action sanity**: price gaps > band must match a known ex-date/split/rights event, else flagged for review.
Each day gets a composite **data-quality score (0–100)**; predictions carry the score of the data they were built on, and alerts are suppressed below a threshold (default 80).

```sql
            max_analog_drawdown, liquidity_risk, execution_risk)
```

Design notes:
- **Never delete**: rows are superseded (validity flags), not removed — the "old knowledge never disappears" requirement is enforced at schema level.
- The DuckDB file (~tens of MB for years of daily data) is committed; raw Parquet is the rebuild source of truth. Weekly `VACUUM` + LFS if it ever exceeds ~100 MB.
- Incremental everything: each pipeline stage reads a `watermarks` table and processes only new dates.

## 7. Obsidian Vault Structure (the persistent memory)

The vault is the human-facing knowledge graph. Code generates and updates the machine sections; human notes are sacrosanct.

```
vault/
├── Home.md                          # dashboard: today's signals, regime, calibration status
├── Companies/<SYMBOL>.md            # one canonical note per listed company
├── Sectors/<Sector>.md
├── Events/YYYY/MM/<event-id>.md     # material events only (materiality ≥ threshold)
├── Predictions/YYYY-MM/<pred-id>.md # every emitted signal, later annotated with outcome
├── Patterns/<pattern-name>.md       # recurring behavioral patterns, confidence-scored
├── Regimes/<period>.md              # regime episodes with entry/exit evidence
├── Evaluations/YYYY-Www.md          # weekly evaluation report
├── Research/                        # HUMAN-ONLY: your notes, hypotheses, paper summaries
├── Journal/YYYY-MM-DD.md            # daily machine journal: what ran, what was seen
└── _meta/                           # templates, taxonomy, vault changelog
```

**Company note anatomy** (machine sections between `<!-- vectora:begin/end -->` markers; anything outside is human and untouched):
frontmatter (symbol, sector, category + history, listing date, flags) → identity & governance summary → fundamentals table (last 8 quarters) → corporate-action history → holdings trend → event log (links to Event notes) → prediction scorecard for this stock (hit rate, calibration, per-setup stats) → pattern tags (links to Pattern notes) → `## Analyst Notes` (human).

**Pattern notes** are the "learning" made visible: each documents a signature (e.g., *volume 5× + price +15% in 5d in Z-category → 30d forward return distribution*), the historical episode list (auto-appended), current confidence score (updated by the evaluation loop), and contradictory observations (appended, never overwritten — per requirement).

**Prediction notes** are the audit trail: emitted signal, full risk block, rendered explanation, then a machine-appended **Outcome** section when resolved. Wiki-links (`[[SYMBOL]]`, `[[pattern-name]]`) make Obsidian's graph view the knowledge graph for free.

Vault regeneration is **incremental and append-safe**: the generator diffs machine sections only. A `vault/_meta/changelog.md` records every machine edit.

## 8. Feature Engineering Specification

~200 features at launch, organized in 10 families. Every feature is declared in `vectora/config/features.yaml` with: name, family, formula reference, **documented economic reasoning** (one sentence minimum, enforced by CI check), lookback, and null policy. The registry doubles as documentation and as the SHAP display-name map.

| Family (count) | Examples | DSE-specific reasoning |
|---|---|---|
| Momentum (25) | returns 1/3/5/10/21/63d; RSI-14; MACD; rate-of-change ranks | Retail herding → momentum persists at short horizons, then sharply reverses |
| Volatility (20) | ATR-14, Parkinson vol, realized vol ratios, GARCH(1,1) forecast, limit-lock frequency | Circuit bands truncate daily moves → limit-lock count is a better "heat" measure than raw vol |
| Liquidity (20) | turnover ৳, Amihud illiquidity, zero-volume days, spread proxy (Corwin-Schultz), volume z-score, free-float turnover | Illiquidity is the #1 practical risk on DSE; also the fuel for manipulation |
| Volume/flow anomaly (20) | volume 5/20/60d ratios, OBV, VWAP deviation, block-trade intensity, up/down volume split | Volume precedes price in accumulation phases documented in DSE pump episodes |
| Technical structure (25) | Bollinger position, Donchian breakout distance, ADX, Stochastic, support/resistance proximity via swing points, gap stats | Standard toolkit; kept because retail participants trade on them (self-fulfilling) |
| Cross-sectional (20) | sector-relative return ranks, market-relative strength, sector rotation deltas, breadth (adv/dec), % of sector above 50DMA | Small market → sector rotation is violent and observable |
| Fundamental (20) | EPS growth, P/E vs sector, NAV discount/premium, NOCFPS/EPS divergence (earnings-quality red flag), dividend yield, days-since-earnings | Audited-vs-cash-flow divergence is a documented DSE red flag |
| Event/calendar (20) | days to/from record date, AGM proximity, board-meeting announced flag, dividend-declaration window, Ramadan/budget/election proximity, post-event drift windows | Announcement-driven drift is strong where diffusion is slow |
| Ownership/governance (15) | sponsor % level & 3m delta, public float %, institute % delta, director-buy event recency, paid-up capital size bucket, category + time-in-category | Low float + sponsor selling is the classic distribution signature |
| Sentiment/attention (15) | news-headline count 7d, lexicon polarity aggregate, Google Trends z-score, first-mention flag, rumor-proxy (price move with zero news) | Attention spikes precede retail inflow; move-without-news flags rumor phases |

Plus **derived meta-features**: historical-analog similarity score (k-NN in feature space against labeled past episodes), pattern-recurrence probability, and regime interactions (feature × regime dummies).

Anti-leakage rules (enforced in the feature engine, tested):
- All features computed with data available **at close of day t** for predictions about t+1…t+H.
- Announcement timestamps: only events scraped before the run's cutoff enter that day's features.
- Corporate-action adjustments applied point-in-time (no retroactive adjusted history leaking splits).
- Fundamentals keyed by **announced_date**, not period_end.

## 9. Prediction System

### 9.1 Targets

A grid of binary classification targets, per stock per day:

- **P(max close-to-close gain ≥ X% within H days)** for X ∈ {3, 5, 10, 20} and H ∈ {1, 3, 5, 10, 30}
- Mirrored downside: **P(drawdown ≥ X% within H days)** (feeds risk engine and exit alerts)
- Specialty heads: P(breakout hold ≥ 5d), P(reversal after 3d run), P(pump-phase → dump within 10d), P(abnormal-volatility day ahead), P(trading-halt/regulatory pause within 10d), P(liquidity trap: cannot exit 1% ADV position within 3d without >3% impact — computed, not learned)

Not every cell gets its own model: one LightGBM per (X, H) upside pair (20 models) + downside mirror + 4 specialty models ≈ **45 small models**, each trained on the pooled cross-section (~350 stocks × ~2,500 days ≈ 800k rows). Weekly retrain of all models ≈ 30–40 min on an Actions runner — verified feasible for LightGBM at this scale.

### 9.2 Calibration and intervals

- Raw model scores → **isotonic regression calibration** fit on the trailing out-of-fold year. Calibration is the product: "70%" must mean 70%.
- Return **conformal prediction intervals** for expected move size (split-conformal on quantile regressors for the 10/50/90 percentile forward return) — this delivers the "confidence intervals not point estimates" requirement with distribution-free guarantees.
- Every prediction row stores: probability, calibrated flag, model_id, regime at emission, data-quality score.

### 9.3 Signal admission rules (predictions ≠ alerts)

A prediction becomes a **signal** only if: calibrated P ≥ threshold (per setup type) AND liquidity ≥ floor AND data quality ≥ 80 AND regime-compatible AND not suppressed by risk engine (e.g., pump-phase score high → buy signals blocked, only warnings emitted).

## 10. Model Framework and Comparison

### 10.1 The honest ranking for this problem

Ordered by expected value on ~800k-row daily tabular data with weak signals:

1. **LightGBM / XGBoost / CatBoost** (primary; pick by CV, likely LightGBM for speed) — state of the art for this data shape.
2. **Regularized logistic regression** — mandatory baseline; if GBMs can't beat it out-of-sample, the feature has no signal.
3. **HMM** — regimes only (§11).
4. **k-NN in feature space** — not a predictor but the historical-analog retrieval engine for explanations.
5. **LSTM/GRU/TCN/Transformers/TFT/TabNet** — evaluated in the comparison harness for completeness, but prior expectation is underperformance: too little data, too much noise, non-stationarity. Included so the claim is *demonstrated*, not asserted. CPU-trainable small variants only.
6. **GNNs** — deferred; the graph (sector/ownership links) is thin. Revisit if ownership-network data proves rich.
7. **RL** — simulation-only toy in Phase 6+; never a signal source.

### 10.2 Comparison harness (`vectora/train/compare.py`)

- **Walk-forward evaluation**: expanding window, retrain every 26 weeks in backtest, embargo gap of max(H) days between train and test to kill horizon leakage. No random k-fold, ever.
- Metrics per model per target: AUC, PR-AUC, **Brier score** (primary — it prices calibration), calibration curve, and an **economic backtest**: top-decile signal portfolio with DSE-realistic frictions (0.4% round-trip commission+fees, slippage = f(order size / ADV), 1-day execution lag, circuit-band fill limits, T+2 settlement lockup).
- Champion/challenger: new model families or feature sets run as challengers for ≥ 8 weeks of paper predictions before promotion. `model_registry` tracks lineage.
- Ensembling: simple probability averaging of top-2 families if it improves Brier on validation; nothing fancier.

### 10.3 Floor-price eras and other data pathologies

2020 and 2022–2024 floor-price periods produced frozen prices and phantom liquidity. Treatment: era dummy features + exclusion of frozen-stock rows from training labels (a stock pinned at floor has no usable label) + regime flag so the model knows "this can happen again."

## 11. Market Regime Detection

Two-layer approach, both cheap:

1. **Rule layer** (interpretable, immediate): DSEX 50/200DMA state, 21d realized vol percentile, breadth (% above 50DMA), aggregate turnover percentile, new-highs/new-lows. Maps to the taxonomy: Bull / Bear / Sideways / Panic / Recovery / Speculative-heat (turnover+vol spike with weak breadth) / Low-liquidity.
2. **HMM layer** (statistical): 3–4 state Gaussian HMM on daily index returns + turnover; provides regime probabilities and change-point alerts. Accumulation/Distribution are detected per-stock (OBV divergence + sponsor-holding deltas), not market-wide.

Uses: regime is a model feature; signal admission is regime-gated (e.g., breakout longs disabled in Panic); regime *changes* are themselves alerts; evaluation is reported per-regime (a model that only works in bull markets gets caught).

## 12. Event Intelligence (no-LLM design)

### 12.1 Event taxonomy and rule classifier

DSE/BSEC announcement titles are highly formulaic ("...has informed of a Board Meeting...", "...recommended 10% cash dividend...", "Trading of the shares of ... will remain suspended..."). A regex/keyword rule classifier over titles achieves high precision for a ~30-type taxonomy:

`dividend_declared` (cash/stock %, parsed), `earnings_release` (EPS parsed), `board_meeting_scheduled`, `agm_notice`, `record_date`, `rights_issue`, `category_change` (from→to parsed), `trading_halt/resume`, `spot_market_move`, `director_buy/sell_intent`, `sponsor_share_transfer`, `qfi/placement`, `bsec_enforcement`, `price_sensitive_other`, `no_price_sensitive_info` (the classic reply to DSE queries — itself a signal), `unclassified` (routed to vault for human review; taxonomy grows over time).

Each event gets: type, parsed parameters, **polarity** (from type + parameter sign, e.g., dividend above/below last year), **materiality** (type prior × deviation from expectation), and links into the features and alert pipelines.

### 12.2 Event-impact estimation

For each event type (and key parameter buckets), maintain an **event-study table**: historical distribution of abnormal returns at t+1, t+3, t+5, t+10 following that event type, split by regime and category. New event → immediate impact estimate = historical distribution + current-context adjustment (liquidity, regime). This is the "immediately estimate market impact" requirement, done statistically.

### 12.3 Pre-announcement pattern detector

The requirement "learn how public behavior changed around events that later became public": for every material event, look back 10 trading days and record volume/price/volatility z-scores. Over time this builds a labeled dataset of *pre-event footprints*. A dedicated model scores current stocks for "resembles a pre-announcement footprint" — emitted as an **information-asymmetry warning** (elevated risk + possible opportunity), never as an accusation. Purely descriptive of public data.

## 13. Z-Category Specialist Module

Z-category stocks get dedicated treatment because their dynamics differ structurally (weak fundamentals, low float, margin restrictions, episodic speculative rallies, higher manipulation incidence per BSEC enforcement history):

- **Separate model heads**: the pooled models include category features, but Z stocks additionally get Z-only models trained on the Z subsample (smaller data, stronger priors, higher alert thresholds).
- **Z lifecycle tracking**: `category_history` powers studies of demotion→rally→re-promotion cycles; the vault gets a `Patterns/z-category-cycle.md` note with episode statistics (entry drawdown, time-in-Z, rally frequency/magnitude, re-promotion hit rate).
- **Pump-and-dump phase model**: 4-phase state machine (quiet accumulation → markup → distribution → collapse) scored per Z/B stock daily, features: volume ramp shape, price-vs-volume divergence, float turnover velocity, news vacuum during rise, historical episode similarity. Training labels assembled in Phase 4 from (a) price/volume signature rules and (b) publicly reported BSEC enforcement cases as high-confidence anchors.
- **Hard risk posture**: Z signals always carry: liquidity-trap probability, "exit may take N days" estimate, regulatory-pause probability, and a mandatory warning block in alerts. Buy-side Z signals are capped at urgency ≤ Medium regardless of probability (opportunity exists, but the system never screams "buy" on a Z stock).

## 14. Risk Engine

Attached to every prediction before it can become a signal/alert:

| Field | Method |
|---|---|
| Confidence score | Calibrated probability × data-quality × model-health (recent Brier trend) |
| Expected upside / downside | Conformal 10/50/90 forward-return quantiles |
| Volatility estimate | GARCH(1,1) or EWMA fallback |
| Risk/reward | median upside ÷ |P10 downside| |
| Max analog drawdown | Worst drawdown across k=20 nearest historical analogs |
| Liquidity risk | Position-exit model: days to unwind 1% ADV at ≤1% impact; Amihud percentile |
| Execution risk | Circuit-band proximity, halt frequency, spread proxy |
| Regulatory risk | P(halt/pause) head + active-enforcement flag |
| Data quality | From §5.3 |

Portfolio-level guidance (not execution): suggested max position % given liquidity, and a concentration warning if outstanding signals cluster in one sector.

## 15. Explainability

Every signal renders a structured explanation from four ingredients — no free-text generation needed:

1. **Drivers**: top-6 SHAP features with registry display names and directional phrasing ("21-day volume ratio is 4.2× — historically the strongest contributor to this setup").
2. **Historical analogs**: k-NN retrieval of the most similar past episodes (same feature space), each linked to its vault note, with their realized outcomes ("12 similar setups since 2015: 8 hit +10% within 10d, median max drawdown −4%").
3. **Uncertainties & failure modes**: templated from risk block ("thin book — a single large seller invalidates this", "earnings due in 3 days — binary event risk", "regime is Speculative-heat, where this setup's hit rate drops to 41%").
4. **Alternative scenario**: the mirrored downside probability, stated plainly.

Template output reads like a disciplined analyst note and is fully audit-traceable to numbers.

## 16. Alerts (email)

**Channels**: Gmail SMTP → your inbox. Two message classes:
- **Daily digest** (post-close, always sent): regime, top signals with risk blocks, event roundup, watchlist changes, yesterday's outcome resolutions, calibration snapshot. HTML email, also saved to `reports/`.
- **Urgent single alerts** (intraday scans + material events): only urgency ≥ High.

**Urgency ranking** = f(calibrated probability, expected move size, time sensitivity, liquidity, novelty). Anti-fatigue rules: max 3 urgent emails/day (overflow rolls into digest), per-symbol cooldown 48h unless urgency increases a tier, deduplication against open signals, quiet hours (no urgent sends 22:00–08:00 Dhaka), weekly alert-precision report (of alerts sent, how many mattered) feeding threshold auto-tuning.

Alert taxonomy: high-confidence entry setup / exit signal on open position-signal / volume anomaly / director-buy disclosure / abnormal volatility / regulatory action / category change / regime change / pump-warning / data-quality failure (system health).

## 17. Self-Evaluation and Continuous Learning

The loop that makes it "learn":

1. **Outcome resolution** (daily pre-open): every matured prediction → realized return, hit/miss, max favorable/adverse excursion, days-to-threshold.
2. **Calibration accounting** (weekly): reliability curves per model/regime/category; Brier decomposition; hit-rate by setup type. Written to `Evaluations/` in vault + email summary.
3. **Error autopsy** (rule-based): each miss tagged with a cause hypothesis from a fixed taxonomy — event shock (halt/news within window), regime shift mid-horizon, liquidity failure (couldn't have executed anyway), data-quality issue, or model error (residual). Tags accumulate on Pattern notes.
4. **Confidence evolution**: per-pattern confidence scores updated Bayesianly (Beta-binomial on hit/miss counts); contradictory observations appended to Pattern notes, never overwritten.
5. **Retrain policy**: scheduled weekly retrain on expanding window; **triggered** retrain if rolling 4-week Brier degrades > 20% vs training-time expectation or a regime change is confirmed; challenger evaluation gate before any promotion (§10.2).
6. **Feature lifecycle**: features with ~zero SHAP mass for 26 weeks are flagged for retirement (kept in registry, dropped from training) — the registry documents *why*, preserving knowledge.
7. **Threshold auto-tuning**: alert admission thresholds adjusted quarterly to hold alert precision above target (default: ≥ 60% of High-urgency entry alerts should reach ≥ half their target move).

This closes every requirement: predictions→feedback, outcomes→improvement, mistakes→training data, successes→confidence.

## 18. Lessons Taken from Comparable Systems

Brief, because the value is in what we adopt: **TradingView/TrendSpider** → alert UX: one-line "what + why + so-what", deep link to detail (our vault note). **Bloomberg** → the terminal's power is cross-linked context; our wiki-links replicate this at $0. **Numerai** → rigorous walk-forward + meta-model humility; era-based validation inspired our embargoed walk-forward. **QuantConnect/OpenBB** → open, modular pipeline architecture; OpenBB confirms scraping-first data layers are viable products. **AlphaSense/Kavout** → event-driven scoring, but their NLP depth needs LLMs — our rule classifier is the honest free version. **FinGPT** → noted as the Phase-6 upgrade path, not the base. **Academic emerging-market literature** → momentum + illiquidity premia are stronger and manipulation footprints are detectable in frontier markets; herding indices (CSAD) worth adding as a market feature (in feature backlog).

## 20. Deployment, Monitoring, Security

**Deployment**: everything is `git push`. Workflows pin Python version and dependency lockfile (`uv` for fast, reproducible installs — Actions cold-start matters). Each workflow commits its outputs (data, vault, reports) with a bot identity; concurrency groups prevent overlapping runs.

**Schedules** (UTC; Dhaka = UTC+6, DSE trades Sun–Thu 10:00–14:30 local):
- intraday-scan: `0 4,5,6,7,8 * * SUN-THU` (10:00–14:00 Dhaka hourly)
- eod-pipeline: `30 9 * * SUN-THU` (15:30 Dhaka, after archive settles)
- evaluate: `0 3 * * SUN-THU` (09:00 Dhaka, pre-open)
- train: `0 6 * * FRI` (market closed)
- health: daily 
GitHub cron drift (up to ~15 min) is acceptable at our cadence.

**Monitoring**: `health.yml` checks: last successful run per workflow, data freshness (max date in DB vs calendar), layout-canary status, data-quality trend, Actions minute burn rate. Any failure → email with the failing stage and log excerpt. Workflow failures also surface natively via GitHub notification email.

**Security**: Gmail app password + any future tokens live only in GitHub Secrets; repo private; no PII anywhere; scraper User-Agent identifies the project honestly; secrets never logged; branch protection on `main` optional (single user). Threat model is modest: the main risks are secret leakage in logs (mitigated: no secret interpolation in echo/log lines) and supply-chain (mitigated: lockfile + dependabot).

## 24. Known Limitations and Risks (stated honestly)

1. **Scraping fragility** — dsebd.org redesigns break collectors. Mitigation: canaries, fixtures, raw-layer replay, AmarStock fallback. This is the #1 operational risk.
2. **EOD granularity** — "immediate-term" is bounded by hourly snapshots; true intraday alpha is out of reach for free.
3. **Small data** — ~350 stocks × ~13 usable years limits model complexity; expect modest, regime-dependent edges, not oracle accuracy. Calibration honesty is the defense.
4. **Non-stationarity** — floor prices, rule changes, market-structure evolution mean past patterns decay; the learning loop is designed for this but cannot eliminate it.
5. **Survivorship** — delisted-company history is hard to recover; backfill will be imperfect; noted in every backtest report.
6. **Gmail/Trends unofficial limits** — pytrends and SMTP can throttle; both are best-effort tiers.
7. **GitHub Actions** — cron drift, occasional runner outages; the health watchdog and idempotent stages make missed runs self-healing (next run backfills).
8. **Legal/ethical** — public-data scraping at polite volume for personal research; no redistribution; no advice; manipulation detection outputs are pattern warnings about *securities*, never accusations against *persons*.
